补充:LIKE 前缀优化的前提(case_sensitive_like / NOCASE 索引)
默认 LIKE 大小写不敏感 + BINARY 索引 => 不能转 range:

--- PLAN [LIKE 默认] ---
SQL: SELECT id FROM orders WHERE email LIKE ?
params: ('user1%',)
  SCAN orders USING COVERING INDEX idx_orders_email
PRAGMA case_sensitive_like=ON 后 => 可转 range:

--- PLAN [LIKE csl=ON] ---
SQL: SELECT id FROM orders WHERE email LIKE ?
params: ('user1%',)
  SEARCH orders USING COVERING INDEX idx_orders_email (email>? AND email<?)
默认 LIKE + COLLATE NOCASE 索引 => 也可转 range:

--- PLAN [LIKE + NOCASE 索引] ---
SQL: SELECT id FROM orders WHERE email LIKE ?
params: ('user1%',)
  SEARCH orders USING COVERING INDEX idx_orders_email_nocase (email>? AND email<?)

补充:无类型声明列的混合存储类(正确性陷阱,不是性能问题)
  WHERE v = 123   -> [(1, 'integer')]
  WHERE v = '123' -> [(2, 'text')]

--- PLAN [mixed v='123'] ---
SQL: SELECT rowid FROM mixed WHERE v = ?
params: ('123',)
  SEARCH mixed USING COVERING INDEX idx_mixed (v=?)
  两次查询都走索引,但各自只能命中同存储类的行。

实验 7:WITHOUT ROWID vs rowid 表 + 唯一索引
==============================================================================
users_rowid:普通 rowid 表 + UNIQUE INDEX(email)
users_wr   :WITHOUT ROWID,email 即主键(表本身就是一棵索引 B-tree)
各对象占用存储(dbstat, 单位 KB):
  orders                    10328.0 KB
  idx_orders_cust_status_date   2784.0 KB
  idx_orders_email_nocase    2604.0 KB
  idx_orders_email_lower     2604.0 KB
  idx_orders_email           2604.0 KB
  t_ab                       2560.0 KB
  t                          2384.0 KB
  idx_orders_status_amount   2288.0 KB
  idx_orders_created         1840.0 KB
  idx_orders_status          1408.0 KB
  users_wr                    192.0 KB
  users_rowid                 184.0 KB
  users_rowid_email           156.0 KB
  sqlite_stat1                  4.0 KB
  sqlite_schema                 4.0 KB
  mixed                         4.0 KB
  idx_mixed                     4.0 KB
  => users_wr(表即索引) vs users_rowid(表)+users_rowid_email(索引)

--- PLAN [rowid 表 UNIQUE 索引] ---
SQL: SELECT name FROM users_rowid WHERE email = ?
params: ('user123@example.com',)
  SEARCH users_rowid USING INDEX users_rowid_email (email=?)

--- PLAN [WITHOUT ROWID 主键] ---
SQL: SELECT name FROM users_wr   WHERE email = ?
params: ('user123@example.com',)
  SEARCH users_wr USING PRIMARY KEY (email=?)
  点查: rowid表+索引 0.0124 ms | WITHOUT ROWID 0.0118 ms
  点查: rowid表+索引 0.0126 ms | WITHOUT ROWID 0.0117 ms
  点查: rowid表+索引 0.0128 ms | WITHOUT ROWID 0.0118 ms

--- PLAN [rowid表 range(经唯一索引)] ---
SQL: SELECT email, name FROM users_rowid WHERE email BETWEEN ? AND ?
params: ('user100@', 'user200@')
  SEARCH users_rowid USING INDEX users_rowid_email (email>? AND email<?)

--- PLAN [WITHOUT ROWID range(直接扫表)] ---
SQL: SELECT email, name FROM users_wr   WHERE email BETWEEN ? AND ?
params: ('user100@', 'user200@')
  SEARCH users_wr USING PRIMARY KEY (email>? AND email<?)
  range 查: rowid表+索引 0.475 ms | WITHOUT ROWID 0.429 ms

结论方向:WITHOUT ROWID 主键表少一次'索引->rowid->表'的跳转,
且省掉独立索引的存储;适合'自然主键 + 整行小'的表。
