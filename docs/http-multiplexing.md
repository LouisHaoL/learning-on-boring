# HTTP/1.1 vs HTTP/2:多路复用与队头阻塞

> 本文的耗时数据均来自本机真实实验(localhost 回环,2026-09-06),
> 命令与完整输出见 `experiments/http-multiplexing/README.md`。
> 环境:Windows 10 / Python 3.14.4 / hypercorn + httpx[http2] + h2 库;
> 本机 curl 8.18.0 未编入 nghttp2,帧级观察改用 Python h2 库直连。
> 文中明确区分【实测】与【文档知识】:标"实测"的论断都有对应实验;
> 标"文档知识"的来自 RFC 7540/9112 等规范,实验只做机制演示。

## 0. 一句话总结

HTTP/1.1 的连接是"独占通道":一个请求不结束,这条连接上就什么都不能干;
想并发只能开更多 TCP 连接。HTTP/2 把"请求/响应"拆成带编号的帧流(stream),
让几十个请求共享一条连接而互不阻塞——但它们仍共享同一个 TCP 字节流,
所以 TCP 层的丢包重传还是会卡住所有 stream,这就是催生 HTTP/3/QUIC 的残余队头阻塞。

## 1. HTTP/1.1:keep-alive、管线化与队头阻塞

### 1.1 从短连接到 keep-alive【文档知识】

HTTP/1.0 默认每个请求新建一条 TCP 连接,用完即断:三次握手 + 慢启动
在每次请求时都要重付一遍。HTTP/1.1 默认 `Connection: keep-alive`,
连接复用后握手成本只付一次,TCP 拥塞窗口也能维持。

但 keep-alive 只解决了"重复握手",没解决"串行"。HTTP/1.1 的报文是
纯文本、无编号的,请求和响应在一字节流里必须严格一一配对:

```
HTTP/1.1 单连接时间轴(每个资源 50ms 服务端延迟,实测场景)

请求:   [A---][B---][C---][D---][E---][F---]      串行排队
响应:         [A][B][C][D][E][F]
时刻:   0    50   100  150  200  250  300 ms
```

请求 B 在 A 结束前连字节都发不出去。实测(实验一,24 个资源 × 50ms):

| 策略 | 中位总耗时 | 理论下限 |
|---|---|---|
| 单连接 keep-alive 串行 | **1235.5 ms** | 24×50 = 1200ms |
| 6 并发连接 | 216.9 ms | 4×50 = 200ms |
| 100 并发连接 | 57.5 ms | 50ms |

这组数据同时解释了浏览器的"每 host 6 连接"限制【文档知识】:
它不是技术上限,而是浏览器在"并发收益"和"每条连接的握手/内存/拥塞
窗口冲击"之间做的折中——6 条连接把 24 个资源从 24 个串行批次压到 4 个。

### 1.2 管线化(pipelining)为什么失败【实测 + 文档知识】

HTTP/1.1 规范允许在收到响应前把多个请求一次性写进连接(pipelining),
但**要求响应必须按请求顺序返回**。我直接用原始 socket 验证了这一点:
在一条连接上 t=0 把 24 个请求全部写出,

```
请求:   [ABCDEFGH...全部在 t=0 发出]
响应:   [A][B][C][D][E][F][G][H]...          ← 仍按序排队吐出
时刻:   0    50 100 ...                      ← 与串行几乎没差别
```

实测结果:总耗时 1164.1 ms,和纯串行(1235.5ms)几乎相同;
更致命的证据是"前 1/4 字节直到 ~303 ms 才到达"——≈ 前 6 个响应
串行完成的时间。也就是说,即使所有请求早已躺在服务器门口,
响应字节仍被"按顺序"这条规则强制排队。

管线化被废弃的另外两个原因【文档知识】:
1. **队头阻塞(head-of-line blocking)依旧**:响应 1 慢,响应 2..N 全卡住,
   客户端甚至无法提前取消。
2. **中间盒不兼容**:不少老代理/负载均衡器会破坏性地处理管线化请求
   (错序转发、拆散配对),导致响应错位,属于正确性问题而不只是性能问题。
   浏览器默认关闭管线化,只靠多条连接 + 并行发起新连接来提并发。

curl 的毫秒级 trace 佐证了同连接串行:第二条请求的"发出时刻"恰好等于
第一条响应的"完成时刻",两条 300ms 的请求总耗时 603ms ≈ 2×300ms。

### 1.3 连接数扩展曲线:加连接的收益与代价【实测 + 文档知识】

把连接池从 1 扫到 24,看同一批资源(24 × 50ms)的完成时间:

```
连接数      中位耗时ms    相对单连接    边际收益(相对上一档)
   1         1222.3       1.00x        1.00x
   2          625.3       1.95x        1.95x
   3          410.7       2.98x        1.52x
   4          324.7       3.76x        1.26x
   6          217.9       5.61x        1.49x
   8          155.7       7.85x        1.40x
  12          123.6       9.89x        1.26x
  24           57.8      21.15x        2.14x
```

加速比 ≈ 资源数 / 连接数:总工作量固定,分给 k 条连接就除以 k,
数据形态本身没有"6 的魔法"。浏览器选 6 的真正原因在**成本侧**
【文档知识】:

- 每条连接都有 TCP 握手、TLS 握手、内核缓冲与服务端并发上下文的开销;
- 客户端的总连接数预算有限,某个 host 占太多会饿死其他 host
  (Chrome 对总连接数另设上限);
- 多条连接各自慢启动,会加剧拥塞、与单条大带宽连接竞争,网络条件差时
  反而拉长长尾。

所以工程折中落在"6":对典型页面的几十个资源,6 条连接已把串行批次
压缩到可接受,又不至于把成本和拥塞推高。而 HTTP/2 直接把这个折中取消了
—— 一条连接内部就有并发,连接数的收益/成本权衡不再需要客户端做
(见 §2.2 实测:1 条 h2 连接胜过 24 条 h1.1 连接)。

### 1.4 一个常见误区:"并发连接"加速的是握手不是排队

实验一中 6 连接相对单连接提速 5.6 倍,不是因为"6 条连接传输更快",
而是因为**排队的串行性被打断**:HTTP/1.1 的延迟来自"同连接上前一个响应
不结束、下一个请求不能发"。多开连接绕开的是应用层的串行约束,传输
本身的带宽从未是瓶颈(本实验每个响应仅 2KB)。理解了这一点,"h2 多路
复用到底复用了什么"就很直观:复用的是连接承载并发的资格,把
"每条连接一个并发"变成了"每条连接任意多并发"。

## 2. HTTP/2:二进制分帧、流与多路复用

### 2.1 二进制分帧层【文档知识】

RFC 7540 在应用层内引入了一个"分帧层":所有通信切成带 9 字节头的帧
(Length + Type + Flags + Stream Identifier)。常见帧类型:

| 帧类型 | 作用 |
|---|---|
| HEADERS | 传递首部块(经 HPACK 压缩),开启一个 stream 的响应/请求 |
| DATA | 传输请求/响应体,是"数据被切开交错"的载体 |
| SETTINGS / SETTINGS_ACK | 连接级参数协商(如初始流量窗口、最大帧大小) |
| WINDOW_UPDATE | 流量控制:每个 stream 和整条连接各有滑动窗口 |
| PING / GOAWAY | 探活 / 优雅关闭 |
| PRIORITY(已废弃) | 流优先级建议树(RFC 9113 中移除,见 §2.4) |

关键点:**stream id 给报文重新建立了配对关系**。HTTP/1.1 靠"顺序"配对,
HTTP/2 靠"编号"配对,于是顺序可以随意交错:

```
HTTP/2 单连接,三个 stream(A 慢 150ms,B 中 100ms,C 快 50ms)

字节流(单条 TCP 连接内):
  HEADERS(A) HEADERS(B) HEADERS(C)
  DATA(C#1) DATA(B#1) DATA(C#2) DATA(A#1) DATA(B#2) DATA(A#2) ...
            ↑ B/C 的数据不用等 A 完成

stream 完成时间轴(与 1.1 同参数时):
  C: 0────────────50ms 完成
  B: 0──────────────────100ms 完成
  A: 0─────────────────────────────150ms 完成
```

### 2.2 多路复用实测【实测】

同一台服务器(同一端口,TLS ALPN 协商 h2 或 h1.1),同一资源集
(24 个 × 50ms 延迟),客户端只改变"协议 + 连接数上限":

| 方案 | 中位总耗时 | 相对 h2 |
|---|---|---|
| HTTP/2,1 条连接,24 个 stream | **73.7 ms** | 1× |
| HTTP/1.1,1 条连接 | 1480.8 ms | 20× |
| HTTP/1.1,6 条连接(浏览器策略) | 259.0 ms | 3.5× |
| HTTP/1.1,24 条连接 | 103.0 ms | 1.4× |

两个实测结论:
1. h2 用一条连接打平甚至超过 h1.1 开满 24 条连接——多路复用让"连接数"
   这个性能旋钮失效了,这也是 h2 敢砍并发连接数(浏览器实际用 1 条)的底气。
2. h1.1 的六连接策略比单连接快约 5.7 倍(1480→259ms),但仍比 h2 慢 3.5 倍,
   且多出的连接成本(握手、内存、服务端线程)是 h2 不需要付的。

### 2.3 帧级证据:响应乱序完成【实测】

用 h2 库裸写客户端,单连接发出 6 个请求(延迟按 150/100/50ms 交错),
记录每个收到帧的时间戳和 stream id:

```
   t(ms)  帧            stream   说明
     0.2  SETTINGS       0      连接参数协商
    63.5  HEADERS        5      ← 50ms 的响应先完成
    63.6  HEADERS       11      ← 和另一个 50ms 的响应并列完成
    63.7  DATA           5
    63.7  END_STREAM     5
   110.3  HEADERS        3      ← 100ms 组完成
   110.6  HEADERS        9
   155.8  HEADERS        1      ← 150ms 组最后完成
   156.0  END_STREAM     7

交错统计:12 个 DATA 帧中 5 次 stream id 切换,来自 6 个不同 stream
```

先发的不先回:stream 5/11(50ms)在 ~64ms 完成,先发的 stream 1(150ms)
要等到 ~156ms。HTTP/1.1 下同连接完成顺序永远是请求顺序,不存在交错。
注意该实验中 DATA 未出现"半截交错"(每个响应体只有 512B,小于
hypercorn 的帧大小,所以每个 stream 一次 DATA 就带完);真实大响应下
DATA 会在字节级交替,上面的 stream id 切换统计就是对交错现象的度量。

### 2.4 HPACK 与流优先级【文档知识】

- **HPACK**:HTTP/1.1 每次请求都带几百字节重复的文本头。h2 的 HPACK 用
  三招压缩:静态表(61 个常见头字段)、动态表(连接级缓存,后续请求
  引用索引即可)、Huffman 编码。RFC 7541。安全上的教训是必须防
  "压缩预言攻击",所以 HPACK 用确定性的表索引而非通用压缩。
  (本实验未单独测头部压缩收益——响应体实验刻意规避了头部体积的影响,
  实测 + 分析可另行展开。)
- **流优先级**:h2 原设计让客户端声明 stream 依赖树(关键 CSS 先于图片),
  服务器按权重分配带宽。但实现复杂、浏览器与服务器行为不一,实践中
  收益不明确,RFC 9113 已将 PRIORITY 帧和依赖树废弃;现代方案是
  PRIORITY_UPDATE 扩展(RFC 9218)或直接靠"客户端发起顺序"隐式表达。
  本实验未测优先级(测试端点同构,无关键/非关键资源之分)。

## 3. 残余问题:TCP 层的队头阻塞与 HTTP/3

### 3.1 h2 只解决了应用层队头阻塞【文档知识 + 机制分析】

h2 的所有 stream 共用**一条 TCP 字节流**。TCP 只认识字节序号,不认识
stream:一旦某个报文段丢失,接收方必须等它重传到达才能把后续字节交给
应用——哪怕丢的字节属于 stream A,stream B/C 的已到达数据也交不出来。
这就是 TCP 层队头阻塞:

```
TCP 层丢包时(h2 over TCP):

应用可见的 stream:  A: ████░░░░░░   B: ████░░░░░░   C: ████░░░░░░
                          ↑ 丢一个报文段 → 三个 stream 同时停摆等重传
TCP 字节流:         ... seq=1000 [丢] seq=1100(已到) seq=1200(已到) ...
                              ↑ 内核必须等 seq=1000 补上才向上交付
```

弱网/高丢包环境下,h2 单连接反而可能比 h1.1 六连接更差:
h1.1 丢包只阻塞它所在的连接,其他 5 条照常;h2 丢一个包全线暂停。
实测佐证的旁证:本实验 localhost 无丢包,h2 优势为 3.5×;丢包环境下的
反转是文档与业界共识,本实验环境无法直接复现(标注:未实测)。

### 3.2 HTTP/3(QUIC)的机制性回答【文档知识】

HTTP/3 把传输层从 TCP 换成基于 UDP 的 **QUIC**:
1. QUIC 原生理解 stream:丢包只阻塞它所属的 stream,其余 stream 的数据
   照常交付——传输层消灭队头阻塞。
2. 握手合并:TLS 1.3 内嵌进 QUIC,1-RTT 甚至 0-RTT 建连
   (TCP+TLS 1.2 要 3-RTT);连接用 Connection ID 标识,IP 切换
   (Wi-Fi→蜂窝)不中断。
3. 头部/帧同样二进制化,HPACK 换成专为 QUIC 设计的 QPACK
   (为避免动态表自身的队头阻塞做了取舍)。
代价:QUIC 用户态实现带来的 CPU 开销,以及 UDP 在部分中间盒受限。
本课题实验止步于 1.1 vs 2;3 只做机制对比。
