# mini-db:单文件嵌入式 KV 存储引擎

用纯 Python 标准库实现的教学级存储引擎,目的是把数据库最核心的三个机制
亲手做一遍:**页式存储、以页为节点的 B+ 树、Write-Ahead Log 与崩溃恢复**。
没有删除操作(免掉 B 树合并),单进程单写者,其它都按真数据库的套路来。

```
demos/mini-db/
├── pager.py        页式存储:4KB 页、页 id 寻址、元数据页、脏页管理
├── btree.py        B+ 树:节点=页,插入/点查/范围扫描/分裂,不变量自检
├── wal.py          Write-Ahead Log:定长头+变长 payload+CRC32,撕裂检测
├── db.py           事务与恢复:begin/commit/rollback、put/get/scan、重放
├── cli.py          命令行接口(可选)
├── tests.py        152 项断言,含三类崩溃场景 + 真实子进程死亡测试
├── demo_crash.py   真实杀进程的崩溃恢复演示(两种崩溃窗口)
└── bench.py        性能粗测 + 树高实验(本文所有数字来自真实运行)
```

## 运行方式

```bash
python tests.py        # 全部断言(约 5 秒)
python demo_crash.py   # 真实 kill 子进程的崩溃恢复演示
python bench.py        # 性能与树高实验(含 100 万条插入,约 2 分钟)
python cli.py my.db put hello world
python cli.py my.db get hello
python cli.py my.db stat
```

API 一览:

```python
from db import MiniDB, encode_int, decode_int

db = MiniDB("my.db")              # 打开(或创建);同目录生成 my.db.wal
db.put("name", "claude")          # 自动提交:单条 put 就是一个事务
db.get("name")                    # -> "claude"(值能解码 UTF-8 则返回 str,否则 bytes)

db.begin()                        # 显式事务
db.put("k1", "v1")
db.put("k2", "v2")
db.commit()                       # 或 db.rollback()

db.scan(b"k1", b"k3")             # 范围扫描 [start, end),键以 bytes 返回
encode_int(123)                   # 8 字节大端整数键(数值序==字节序)
db.close()
```

约定:键/值接受 str 或 bytes;键以 bytes 返回(str 只是输入便利,二进制键
无法无损还原成 str,所以不猜);值若为合法 UTF-8 则解码为 str。键 ≤ 200 字节,
值 ≤ 2000 字节(必须和键一起塞进一个叶子页)。

## 一、页式存储(pager.py)

数据文件(`my.db`)被切成固定 **4096 字节**的页,页 id 从 0 开始,
页 pid 在文件中的偏移 = `pid * PAGE_SIZE`。

**0 号页是元数据页**,字节布局(小端):

```
偏移   大小  内容
0      4    magic  "MDB1"
4      4    root_pid    u32   B+ 树根节点页 id(0xFFFFFFFF = 空树)
8      4    page_count  u32   已分配页数(合法 pid ∈ [0, page_count))
12     4084 预留(全零)
```

读写策略:所有页读写经过内存 cache(dict),`write_page` 只改缓存并标脏;
只有事务提交时才调用 `flush_data()` 把脏页写盘 + fsync。**未提交的修改
从头到尾没碰过磁盘文件**,所以回滚(rollback)= 把脏缓存丢掉重读磁盘,
断电的效果与 rollback 完全一致——这是整个引擎原子性的地基。

## 二、B+ 树(btree.py)

每个节点恰好占一个页。键是 bytes,按字节序(memcmp 序)比较。

**叶子页**字节布局:

```
偏移   大小  内容
0      1    type = 1
1      2    num_keys u16
3      4    next_leaf u32   右兄弟页 id(0xFFFFFFFF = 无),范围扫描靠它
7      ...  num_keys 个 entry: klen u16 + key + vlen u16 + value
```

**内部页**字节布局:

```
偏移   大小  内容
0      1    type = 2
1      2    num_keys u16 = 分隔键个数 n
3      4    first_child u32 最左孩子
7      ...  n 个 entry: klen u16 + key + child u32
```

**子树约定**:`children[i]` 子树内所有键 `< keys[i]`,`children[i+1]`
子树内所有键 `>= keys[i]`。等值查找用 `bisect_right(keys, k)` 选分支,
因此分隔键相等的键走右子树。

**分裂**(插入后序列化超过 4096 才触发,按条目数对半切):

- 叶子分裂:右半条目移入新叶,新叶接走原 `next_leaf`,原叶的
  `next_leaf` 指向新叶(叶子链永远完整);分隔键 = 新叶最小键。
- 内部分裂:中间分隔键**上推给父节点**(不留在任何一侧),左右各留
  `mid` 个分隔键与 `mid+1` 个孩子。
- 根分裂:新分配一个内部页做根,`root_pid` 写回元数据页。

分裂沿递归返回值 `(sep, new_pid)` 向上传播,父节点装不下就继续分裂。
没有删除,所以不需要合并/借用,节点最小填充度不做约束(实际利用率
约 50% 起)。

范围扫描:用 `start` 下降到对应叶子,`bisect_left` 定位起点,顺着
`next_leaf` 横向走,直到键 >= end 或链尾。

`btree.check_invariants()` 会递归校验:页内键有序、父分隔键与子树边界
一致、fanout 匹配、**DFS 中序到达的叶子序与 next 指针链接序完全一致**。
tests.py 在 2 万条随机插入后调用它。

## 三、WAL(wal.py)

日志文件(`my.db.wal`)由顺序记录组成,字节布局(小端):

```
+----------+--------+-----------+--------------------+-----------+
| len  u32 | type u8| txid  u64 | payload ...        | crc32 u32 |
+----------+--------+-----------+--------------------+-----------+
   4 字节     1 字节    8 字节      len-21 字节           4 字节
```

- `len`:本条记录总长度;`crc32`:对 `record[4:len-4]` 的校验。
- type:`1 BEGIN` / `2 PUT` / `3 COMMIT` / `4 ABORT`。
- PUT 是**逻辑 redo 记录**:payload = `klen u16 + key + vlen u16 + value`。

**提交协议**(`db._commit_txn`):

```
1. 追加 BEGIN(txid)
2. 逐条追加 PUT(key, value)          <- 事务内所有修改
3. 追加 COMMIT(txid)
4. fsync WAL                          <- 此刻起事务"算数"了
5. 把脏页写数据文件 + fsync
6. 清空 WAL(checkpoint)
```

崩溃只能落在三处,每处都可收敛:

| 崩溃点 | 磁盘状态 | 重启后果 |
|---|---|---|
| 步骤 1-3 之间 | WAL 残缺(无完整 COMMIT) | 撕裂尾部被丢弃,事务不算数 |
| 步骤 4-5 之间 | COMMIT 完整,数据页陈旧 | 重放 WAL,数据页被补齐 |
| 步骤 5 之后 | 数据页已新 | WAL 已被清空,无事可做 |

**恢复流程**(每次 `MiniDB(path)` 打开时执行,`db._recover`):

1. 顺序扫描 WAL;遇到第一条不完整记录(长度不足 / len 非法 / CRC 不符)
   立即停止——写在半路的"尾巴"天然丢弃,这就是 CRC + 定长头的意义;
2. 收集所有出现过 COMMIT 记录的事务 id;
3. 按日志顺序把已提交事务的 PUT 逐条重放进 B+ 树(重放就是普通插入,幂等);
4. 把重放后的脏页刷盘、清空 WAL。

## 四、事务语义

- `begin/commit/rollback`,不支持嵌套;不在事务中调用 `put` 会自动包一层
  单条事务(autocommit)。
- **回滚**:脏缓存丢弃 + 元数据(根指针、页数)回退到磁盘版本,代价 O(脏页数)。
- **原子性**:一个事务的所有修改要么在 WAL 里齐备(重放可复原),要么整体
  不存在;单条操作原子性是它的特例。
- 局限(教学取舍):单进程单写者,无文件锁;无 delete/合并;不支持多事务
  并发隔离;WAL 只保留到最近一次 checkpoint,不提供时间点恢复。

## 五、实验一:崩溃恢复验证(灵魂实验)

`demo_crash.py` 用**真实进程死亡**验证两种崩溃窗口。子进程分 5 批写入
10000 条(每批 2000 条一个事务),父进程在特定时刻直接 `kill` 子进程
(Windows 下为 TerminateProcess,无任何清理),然后重开数据库核对。

实际运行输出(2026-09-06,真实运行,未改动):

```
【场景 A】随机 kill:收到第 2 批回执后随机延时 0~150ms 杀掉子进程
  [父进程] 收到回执: COMMIT batch 0 (rows 0..1999)
  [父进程] 收到回执: COMMIT batch 1 (rows 2000..3999)
  [父进程] 子进程已被 kill(约在第 2 批中途)
  崩溃后磁盘状态:db 文件 180224 字节,WAL 残留 0 字节
  恢复后实际行数:                        4000 条
  恢复重放的事务数:                          0 个
  行数是整批(事务原子性):                  是
  键空间 0..N-1 连续无空洞:              是
  场景 A 结果:通过(commit 的 4000 条完好;被杀批次整体消失)

【场景 B】受控断点:最后一批 WAL fsync 完成后、数据页落盘前 os._exit(1)
  [子进程] COMMIT batch 0 (rows 0..1999)   ... (batch 1-3 同) ...
  [子进程] WAL FSYNCED batch 4, dying before data flush
  崩溃后磁盘状态:db 文件 356352 字节,WAL 残留 78034 字节
  恢复后实际行数:                       10000 条
  恢复重放的事务数:                          1 个
  行数是整批(事务原子性):                  是
  键空间 0..N-1 连续无空洞:              是
  计划 10000 条全部恢复:                是
  场景 B 结果:通过(WAL 重放把已 commit 未刷盘的 2000 条补了回来)
```

### 恢复前后数据对比表

| 场景 | 崩溃点 | 计划写入 | 磁盘 WAL 残留 | 重放事务数 | 恢复后行数 | 已 commit 数据 | 未 commit 数据 |
|---|---|---|---|---|---|---|---|
| A:随机 kill | 批次 3 的内存写入阶段 | 10000 | 0 字节 | 0 | **4000** | 完好 | 整批消失 |
| B:WAL 后数据页前 | `fsync(wal)` 与 `flush(db)` 之间 | 10000 | 78034 字节 | 1 | **10000** | 完好(含重放补回的 2000 条) | 无 |

场景 A 里 commit 阶段只占批次周期约 10%(2000 条 put ≈ 114ms,commit ≈ 13ms),
kill 几乎总落在"未提交修改只在内存"的窗口——这本身就是结论的一部分:
**没写 WAL 的修改根本没碰磁盘**。场景 B 用与 `commit()` 完全相同的前半段
代码 + `os._exit(1)`,把崩溃精确钉在两条 fsync 之间,验证重放路径。
两种窗口的确定性版本都在 `tests.py`(`test_crash_*` 四个测试,含
COMMIT 记录被撕掉 6 字节的撕裂日志测试)。

## 六、实验二:性能粗测

环境说明:Python 3.14.4,Windows 10 x64,Intel 12 代酷睿桌面平台
(`Intel64 Family 6 Model 151`),D 盘为 NVMe SSD(GALAX XA1Q1024N),
文件系统 NTFS。量级参考,非严格基准。

| 实验 | 配置 | 结果 |
|---|---|---|
| 随机 KV 插入(批量) | 100,000 条,每 1000 条一个事务(每事务 2 次 fsync) | **9.1 s ≈ 11,000 行/s** |
| 随机 KV 插入(单条 autocommit) | 500 条,每行一个事务 | **243 行/s**(2.1 s) |
| 点查 | 100k 行中查 200,000 次(9 成命中 + 1 成未命中,热缓存) | **QPS ≈ 950,000** |

解读:两个实验对照能看清 WAL 的代价结构。单条 autocommit(每行一个
事务、2 次 fsync,只写 1 个脏数据页)实测 **243 行/s**(500 条连续 put,
2.1 s)——纯 fsync 频率决定上限。批量化(每 1000 行一个事务)后行吞吐
涨到约 11k 行/s:2 次 fsync 和一次 checkpoint 摊到 1000 行头上,代价
变成每事务约 4MB 的脏页回写(1000 个随机分布的叶子页),瓶颈从
"fsync 次数"转移到"每事务脏页量"。点查是纯内存路径(B+ 树 3 层,
顶层缓存命中),单次约 1 µs,故 QPS 达到百万量级。

## 七、实验三:树结构验证

**有序性**:每个数量级插入完成后,用中序遍历(`scan()`)核验输出严格
升序且与插入集合一致;`tests.py::test_random_stress_vs_dict` 用 3300 次
随机插入(含覆盖)与内存 dict 逐项比对,并调用 `check_invariants()`
校验页内有序、父子边界一致、叶子 next 链与中序一致。

**树高随数据量增长**(顺序插入,每 5000 条一个事务,真实运行):

| 行数 | 树高 | 总页数 | 插入耗时 | 中序遍历有序 |
|---|---|---|---|---|
| 1,000 | 2 | 8 | 0.1 s | 是 |
| 10,000 | 2 | 83 | 0.8 s | 是 |
| 100,000 | 3 | 878 | 8.0 s | 是 |
| 1,000,000 | 3 | 9,268 | 78.7 s | 是 |

百万行只有 3 层、9 千个 4KB 页(约 36MB 文件):一个 4KB 内部页能装约
114 个分隔键,扇出 114^2 ≈ 1.3 万个叶子,覆盖上亿行——这就是 B+ 树
"矮胖"的意义,任何点查最多 3 次页访问(内存里就是 3 次字典查找)。
