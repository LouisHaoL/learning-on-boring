# regex-engine:一个双后端教学正则引擎

用纯 Python 标准库(零第三方依赖)实现的正则表达式引擎,同时实现两种经典后端并对比:

| 后端 | 思路 | 捕获组 | 最坏时间复杂度 |
|---|---|---|---|
| **backtrack** | AST 直接解释执行,深度优先逐路径尝试 | ✅ 支持 | O(2^n),存在 ReDoS 灾难案例 |
| **thompson** | AST → Thompson NFA → 状态集合并行模拟 | ❌ 不支持 | O(m·n),与路径组合数无关 |

(m = NFA 状态数,n = 文本长度)

## 文件结构

```
demos/regex-engine/
├── parser.py     # 递归下降解析器:正则字符串 -> AST(两种后端共用)
├── backtrack.py  # 回溯后端:AST 编译为嵌套闭包(continuation-passing)
├── thompson.py   # Thompson 后端:AST -> NFA 片段拼装 -> 状态集合模拟
├── cli.py        # 命令行入口
├── tests.py      # 断言脚本:双后端一致性 + Python re 交叉验证
├── bench.py      # 性能实验脚本(README 里的数据全部来自它的真实输出)
└── README.md
```

## 运行方式

```bash
# 普通匹配(默认双后端同时跑)
python cli.py '(a|b)*c' 'ababc' --backend both
python cli.py '(\d+)-(\d+)' 'order: 42-2019;'

# 只用某一个后端
python cli.py '^h.*o$' 'hello' --backend thompson

# ReDoS 灾难案例:回溯后端会被步数上限剪断,Thompson 瞬间完成
python cli.py '(a+)+b' 'aaaaaaaaaaaaaaaaaaaaaaaaaaaaX' --backend both

# 测试(全部通过输出 ALL TESTS PASSED)
python tests.py

# 性能实验(生成 README 中的数据表)
python bench.py
```

实际运行输出(Python 3.14.4,Windows):


## 语法支持

| 语法 | 示例 | 说明 |
|---|---|---|
| 字面量 | `abc` | 逐字符匹配 |
| 任意字符 | `.` | 除 `\n` 外任意字符(无 DOTALL) |
| 星号 | `a*` | 0 次或多次(贪婪) |
| 加号 | `a+` | 1 次或多次(贪婪) |
| 问号 | `a?` | 0 次或 1 次(贪婪) |
| 区间量词 | `a{3}` `a{2,}` `a{2,4}` `a{,3}` | 精确 / 下限 / 上下限 |
| 字符类 | `[abc]` `[a-z0-9]` | 支持区间、类内转义 `[\d\-]`、行首 `]` `-` `^` 字面量 |
| 取反类 | `[^abc]` | 匹配类外任意字符 |
| 锚点 | `^` `$` | 仅串首 / 串尾(无多行模式) |
| 捕获分组 | `(a|b)+` | 仅回溯后端报告捕获内容 |
| 非捕获分组 | `(?:ab)+` | 两种后端均支持 |
| 选择 | `cat\|dog` | 左优先(与 Python re 一致) |
| 类转义 | `\d \D \w \W \s \S` | ASCII 语义 |
| 字符转义 | `\. \\ \( \n \t \r \f \v \0` | 标点与控制符 |

**明确不支持**(解析时报 `ParseError`):懒惰量词 `a+?`、反向引用 `\1`、词边界 `\b`、内联标志 `(?i)`、环视 `(?=)`、量词叠加 `a**`、反序区间 `[z-a]`、反序量词 `a{2,1}`。

## 两种后端的架构差异

### 回溯后端:一条路径走到底,失败就回头

`backtrack.py` 把每个 AST 节点编译成一个函数 `fn(text, pos, caps, counter, cont) -> bool`,其中 `cont` 是“后续部分怎么匹配”的延续(continuation)。选择分支按顺序试,量词优先多迭代;任何一步失败,就沿着调用栈回退,换下一条路径重来。

- **为什么有捕获组**:匹配过程是一条具体的时间线。进入分组时在 `caps[2i]` 记下起点、它的延续成功时在 `caps[2i+1]` 记下终点,失败回滚。捕获几乎是“免费”搭在回溯机制上的——这就是 PCRE、Python `re`、Java 都选回溯的原因。
- **为什么会爆炸**:量词嵌套会产生指数条候选路径。`(a+)+b` 对 `"aaaaaaaaaaaaaaaaaaaaaaaaaaaaX"`,每个 `a` 既可以是外层循环的一次迭代、也可以是内层循环的一次迭代,前 24 个 `a` 有约 2^23 种切分方式;匹配失败时引擎必须把每条路都试完才知道“真的不匹配”。

### Thompson 后端:不选路径,全都要

`thompson.py` 用 Thompson 构造法把 AST 编译成 NFA(片段拼接 + 悬空指针回填),然后**同时跟踪所有可能的状态集合**来模拟:每读一个字符,把当前集合里所有能吃掉该字符的状态一起推进,再做 epsilon 闭包。一个位置只有一条路径会走?无所谓,集合里并存即可。

- **为什么线性**:同一位置的状态集合是去重的(`set`),集合大小 ≤ NFA 状态数 m。每个字符做一遍“转移 + 闭包”,总时间 O(m·n),与路径组合数完全无关——没有“回头”这个动作,自然没有灾难回溯。
- **代价**:所有路径被压缩成一个无记忆的状态集合,**没法回答“这个组捕获了什么”**——捕获需要记住“你走的是哪条路径”,而这正是被丢掉的信息。要在线性时间内同时拿捕获组,需要 Pike VM / NFA 线程带 capture slot 的做法(实现复杂度显著上升,本工程未做)。
- **锚点的处理**:`^`/`$` 被编译成带条件的 epsilon 边(仅在 `pos==0` / `pos==len` 时可通过),模拟循环逐位置检查,不需要特判。

## 正确性实验

`python tests.py`,**168/168 项检查全部通过**,包括:

- **116 条语法用例**:字面量、`.`、`*` `+` `?`、`{m,n}` 各种形态(含 `{,n}`)、字符类/取反类/区间/类内转义、锚点(含 `a^b` 这类永不匹配的用法)、分组/非捕获分组/嵌套分组/空分支、全部类转义与标点转义、灾难模式的成功/失败小样本等——两个后端的匹配结果**逐条一致**;
- **与 Python `re` 交叉验证**:上述 116 条用例的匹配结果与 `re.search` 完全一致,另附 10 条硬编码期望值(防止三方差错);
- **捕获组语义**:8 组用例的分组内容、起止位置与 `re.search().groups()` 逐项比对一致(如 `(a+)(b+)` 对 `xxaabbbzz` → `('aa','bbb')`);
- **错误处理**:14 种非法模式(`*a`、`a**`、`[a`、`\q`、`a{2,1}`、`[z-a]`、`^*` …)全部正确抛出 `ParseError`;
- **性能冒烟 + CLI 子进程自检**。

## 性能实验

以下数据全部来自 `python bench.py` 的真实输出(Python 3.14.4,Windows 10,`time.perf_counter` 计时;回溯后端设 20,000,000 步上限防止跑不完)。

### 实验 1:ReDoS 灾难案例 —— `(a+)+b` 对 `"a"*n + "X"`(匹配失败)

| n("a"个数) | 回溯后端 | Thompson NFA |
|---:|---|---|
| 4 | 66.7 us | 17.5 us |
| 8 | 803.6 us | 17.6 us |
| 12 | 12.90 ms | 31.5 us |
| 16 | 209.86 ms | 60.2 us |
| 20 | **3.377 s** | 44.2 us |
| 24 | > 20,000,000 步(剪断) | 51.1 us |
| 28 | > 20,000,000 步(剪断) | 56.6 us |
| 32 | > 20,000,000 步(剪断) | 134.5 us |

回溯后端耗时曲线(对数刻度,1 格 ≈ ×2):

```
n=  4 |#     66.7 us
n=  8 |####    803.6 us
n= 12 |########    12.90 ms
n= 16 |############   209.86 ms
n= 20 |################    3.377 s
n= 24 | (超出步数上限,已剪断 —— 真实耗时为指数级)
n= 28 | (超出步数上限,已剪断 —— 真实耗时为指数级)
n= 32 | (超出步数上限,已剪断 —— 真实耗时为指数级)
```

n 每增加 4,回溯耗时约 ×16(≈2^4):标准的指数曲线。n=20 时已达 3.4 秒,而 Thompson 对同样的失败输入在 n=32 时仍只要 134 微秒——同一输入规模(n=20)下差距已近 **10 万倍(约 5 个数量级)**,且差距随 n 指数拉大,这正是真实世界 ReDoS 攻击的原理。

### 实验 2:匹配成功的情况 —— `(a+)+b` 对 `"a"*n + "b"`

| n | 回溯后端 | Thompson NFA |
|---:|---|---|
| 100 | 114.2 us | 347.4 us |
| 1000 | 1.23 ms | 3.04 ms |
| 5000 | 7.82 ms | 17.02 ms |

注意:匹配**成功**时回溯后端反而更快!贪婪量词一次走通,没有回溯发生,而 Thompson 的集合操作常数更大。这解释了为什么传统引擎在日常场景表现良好——**灾难只出现在“失败”时**,指数条路径必须全部试完才能宣告不匹配。

### 实验 3:Thompson 的线性扩展性 —— 同一模式,失败匹配,n 到十万

| n | Thompson 耗时 | 每字符耗时 |
|---:|---|---|
| 1,000 | 3.05 ms | 3.05 us |
| 10,000 | 32.16 ms | 3.22 us |
| 50,000 | 167.30 ms | 3.35 us |
| 100,000 | 354.19 ms | 3.54 us |

文本长度翻 100 倍,每字符耗时仅从 3.05 us 缓升到 3.54 us(升幅来自状态集合随 n 线性变大时的常数开销)——近似完美的线性扩展。同样规模的输入若交给回溯后端,按实验 1 的指数率外推,n=40 时预计需要数十天,之后 n 每加 4 再 ×16(外推值,非实测)。

## 已知限制

- 无懒惰量词、反向引用、`\b`、环视;`\d\w\s` 为 ASCII 语义;
- `$` 仅匹配串尾,没有 Python re 的“末尾换行符之前”分支;
- 回溯后端用 Python 递归闭包实现,超长文本(数千字符的连续迭代)受递归深度限制;
- Thompson 后端只回答“是否匹配”,不提供捕获组与最长/最左匹配位置。

## 一句话总结

回溯引擎用“时间换功能”(捕获、反向引用都容易加),Thompson 引擎用“功能换时间”(线性保证,但拿不到路径信息)。真实世界的 ReDoS 漏洞,几乎都是前者在错误输入上指数爆炸的直接后果。
